### What the audit means for blue-green

The public entry point is fixed at `127.0.0.1:3579` by a **frozen** tunnel. Nothing local owns that
port except the app itself, and there is no proxy to re-point. Therefore a green instance on
`:3581` cannot receive traffic without one of:

| Option | Mechanism | Cost / risk |
|---|---|---|
| **A. Local front proxy on 3579** | new tiny Node proxy owns 3579, forwards to 3580/3581, switch = in-process pointer flip | new component in the tunnel's path; must proxy SSE/WebSocket correctly; PM2 entry change |
| **B. Two instances on 3579, `SO_REUSEPORT`** | kernel spreads new connections across both | switch is non-deterministic; PM2 supervises one PID only; SSE streams pinned to the old process |
| **C. Atomic `dist/` swap, single process** | build elsewhere, rename into place | **zero downtime for page-only releases** (already in use); server-code changes still restart the process |

Option C is what runs today and needs no approval. Options A and B are **production changes to the
tunnel's origin path** and stop here for your decision (§4 of the brief).

### Front proxy — measured results (2026-11-18 00:35 UTC)

`node dev/release-engine/proxy-selftest.cjs` → **12/12 checks passed**, real sockets, real timing:

| # | Check | Measured |
|---|---|---|
| 1 | HTTP passthrough reaches the active upstream | served by `blue` |
| 2 | POST body forwarded intact | body round-tripped byte-for-byte |
| 3 | SSE chunks stream without buffering | first chunk **405 ms**, stream ended 1208 ms — not buffered |
| 4 | In-flight request survives a switch, stays on its upstream | switched `blue→green` mid-request; response came from `blue` |
| 5 | New requests go to the newly active upstream | `green` |
| 6 | Drain resolves only after the old connection closes | **1309 ms**, remaining 0 (a 1.5 s request was still open) |
| 7 | Active upstream still serves while the other is dead | 200 from `green` |
| 8 | A dead active upstream fails over to the live one | served by `green` |
| 9 | Rollback switch restores the previous release | `green` |
| 10 | WebSocket upgrade tunnels | 101 + echoed payload |
| 11 | Control surface rejects a caller without the token | 403 |
| 12 | Control surface reports real state with the token | active = green |

Three defects were found by the suite itself and fixed:

1. **Keep-alive sockets made `close()` hang.** Node 19+ keeps the global agent's sockets alive, so
   neither the proxy nor the test could ever see zero connections. The proxy now uses `agent: false`
   (one socket per request), which is also what makes "open connections" a knowable number.
2. **`drain()` left a release flagged as draining forever.** After a drain, switching that release
   back to active did not clear the flag, so failover refused to use a live upstream and returned
   502. `switchTo()` now clears it — an active upstream is never draining.
3. **A WebSocket tunnel leaked its connection count.** An upgraded socket half-closes: Node emits
   `end` on our side and no `close` until the socket is destroyed. Counting on `close` alone meant
   such a release could never be reported drained. All terminal events now funnel into one idempotent
   teardown; verified the counter returns to **0**.

**What this does and does not prove.** It proves the switching, draining, failover and rollback
*mechanism* works on real sockets, including streaming and WebSocket. It does **not** prove the real
application runs behind it — that needs the candidate-instance test, which needs the `HAKSTER_DIST_DIR`
override in §5. **No zero-downtime claim is made beyond these measurements.**

**Isolation evidence:** production `dist/index.html` still carries build
`2026-11-18T00:14:13.815Z`, mtime 08:59 — unchanged by any of the prototype runs. The release tree
contains only symlinks; no source file is copied, so no secret is duplicated and no serving file is
writable from the worker.

**Safety rules implemented:** refuses to start below 2 GiB free disk, 400 MiB available memory or
1.5 load/core (it queues instead); one build at a time; deletes nothing, including failed releases;
`mkdir` without `recursive` so an existing release directory is never reused.

**Known limits of the prototype:** it verifies the *artifact*, not the running application (the
server's dist path is hardcoded, so a candidate cannot serve its own dist without the two-line
override proposed below); it does not yet emit into the applet's live-job store; retention of old
releases needs a decision (this project's no-deletion rule means it will grow forever).

## 3. Applet integration (designed, not wired)

The applet already models exactly this job shape (`livejob.cjs`: `begin/stage/heartbeat/finish`,
percent from completed stages, ETA from measured stage medians, `STALE_MS` → UNKNOWN). The mapping:

| Applet field | Prototype event |
|---|---|
| spinner on start | `release.start` |
| stage label / percent | `stage.start` / `stage.end` (`percent`) |
| timestamped updates | `preflight.sample`, `build.output`, `verify.artifact` |
| ETA | `progress().etaSec`, `null` → indeterminate |
| failure + preserved log | `release.failed` + `build.output.tail` |
| stability countdown | after a switch, the existing stability monitor |
| reconnect without restart | the build is a child process; the page only re-reads the journal |

**Not wired on purpose:** the applet reads `dev/build-history/data/current-job.json`, the *same
store the live site reads*. Emitting prototype builds there would show test builds on
haksterai.com. Wiring it is a one-line `livejob.begin()` call in `supervisor.cjs`, gated behind the
approval in §5.

## 4. Dashboard logging (schema, per the brief)

One append-only JSONL record per event, project-tagged, sanitised, read-only to PhantomIDE via the
existing least-privilege feed contract (`/api/build-history/feed`, `feed-credentials.json`):

```
{at, project, release, type, stage,
 commit, version, changedFiles[],            // from git, read-only
 buildId, dir, diskFreeBytes, memAvailableBytes, loadPerCore,
 percent, etaSec, elapsedMs,
 verify:{buildId, files, pages, css, js, bytes},
 approval:{by, at},                          // who authorised the switch
 deploy:{from, to, switchAt, drainedStreams},
 stability:{windowSec, startedAt, passed, state},
 rollback:{at, toBuildId, reason},
 clientImpact:{openStreamsAtSwitch, dropped, reconnects}
}
```

HaksterAI and PhantomIDE records stay in their own files/hosts; PhantomIDE receives only the
sanitised projection, never this journal.

## 5. Approval package (what a production deployment would need)

1. **Affected files**
   - new: `dev/release-engine/*`, `server/src/front-proxy.js` (option A only)
   - changed: `server/src/index.js` — `distPath` becomes `process.env.HAKSTER_DIST_DIR || <current
     hardcoded path>` (default identical; required for a candidate to serve its own build)
   - changed: PM2 process definition (new `hakster-front`, `hakster` moved to 3580) — **config**
2. **Resources:** each release ≈ 4.3 MB + symlinks; 149 GB free → no capacity issue. One build at a
   time at `nice 15`/`ionice 3`; measured 15 s, 4 s warm. Queueing on disk < 2 GiB, mem < 400 MiB,
   load > 1.5/core.
3. **Candidate test results:** artifact verification passes (build id present, 21 pages, 54 files,
   4.24 MB). Application-level readiness is **not yet testable** without the `distPath` override.
4. **Traffic switch:** option A (front proxy on the frozen tunnel's port) preferred; option C
   (dist swap) requires no switch at all and is already live for page-only releases.
5. **Draining:** front stops new connections to the old process, asks open SSE streams to reconnect
   (the applet already reconnects on `retry:`), waits a bounded grace (60 s), then closes.
6. **Rollback:** releases are immutable; switching back is a pointer flip plus a health probe — no
   rebuild, no deletion, no data migration (shared SQLite WAL).
7. **Expected client impact:** page-only releases: none (proven in use). Server-code releases with
   the front proxy: no dropped connections if drain succeeds; without it, the current single
   restart at idle, which is what the applet already reports as APPLYING.
8. **Decision requested:** (a) approve option A, (b) approve the `distPath` override only, (c)
   stay on option C, and (d) set a release-retention policy, since nothing here deletes anything.

**Nothing in this document has been applied.** No production file, service, tunnel or route was
