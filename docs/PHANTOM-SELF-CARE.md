## 2. The three hard laws

### Law 1 — Append, never rewrite

Every change to a brain file is a *new dated section added at the end*. The old text stays,
even when it is stale or wrong. If a fact changed, you add a new entry that says **what
changed, on what date, and why** — you do not go back and edit the old one.

```bash
# correct
printf '\n## %s — %s\n\n- %s\n' "$(date -u +%F)" "what I learned" "the verified fact" >> ~/haksterAi/.hakster/MEMORY.md
```

```bash
# WRONG — destroys history, cannot be undone
cat > ~/haksterAi/.hakster/MEMORY.md <<'EOF'
...shorter, tidier version...
EOF
```

### Law 2 — Backup first, and prove the backup exists

No brain write happens without a unique timestamped copy made moments before, and no write
proceeds until you have confirmed the copy.

```bash
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
cp -p ~/haksterAi/.hakster/MEMORY.md ~/haksterAi/.hakster/MEMORY.md.bak-$STAMP
ls -l  ~/haksterAi/.hakster/MEMORY.md.bak-$STAMP      # must print a real file with a real size
```

Never overwrite an older backup, never reuse a stamp, never `rm` a backup. Backups are kept
forever; they are the only road back.

### Law 3 — Never touch owner config, services, or processes

Read them to diagnose. Do not edit them. Do not stop them. Do not "fix" them.

| Path | Allowed? |
| --- | --- |
| `~/.claude/**` (settings, launcher, models, `ANTHROPIC_BASE_URL`/token, agents, skills) | ❌ read-only. The owner's Claude CLI runs on DeepSeek via Ollama; it is working and is **not** a troubleshooting target |
| `~/.ollama/**` | ❌ read-only |
| `~/.bashrc`, `~/.profile`, `~/.bash_aliases`, `~/.gitconfig`, `~/.ssh/**`, `~/.config/**` | ❌ read-only |
| `~/.pm2/**`, pm2 ecosystem files, `dump.pm2` | ❌ read-only, no `pm2 save`/`pm2 dump` unless asked |
| any `server/.env`, `.env.local`, `.env.production.local`, key/credential file | ❌ read-only |
| `/etc/cloudflared/config.yml`, `~/.cloudflared/**`, tunnel credential JSON | ❌ read-only — never restart, repoint, or run DNS commands against a tunnel |
| `~/mint-backup/**` | ❌ read-only — config source of truth |
| your brain files (table above) | ⚠️ append only |
| application source, UI, docs, new files, backups | ✅ normal work |

If a config change is genuinely required: **name the exact file, the exact diff, and the
consequence, then wait for an explicit yes for that exact file.** Silence is not approval, and
approval given for one file never transfers to another.

Processes follow the same barrier: never kill, stop, restart, or reprioritize a process or
service to lower a number or clear a duplicate. Identify it read-only, report it with the
measurement, and let the owner decide.

## 3. The 60-second checklist before any brain write

Answer all six. If any answer is "no" or "not sure", do not write.

1. Is this file in the brain table? If no → it is not a brain write; use normal rules.
2. Am I **appending** a new dated section, not editing existing lines?
3. Did I take a unique timestamped `.bak-<stamp>` copy *and* confirm it with `ls -l`?
4. Is my new text factual, verified against the running system, and free of secrets?
5. Does the file still have its previous size + my addition (never smaller)?
6. Can I say out loud what the file looked like before, and how to get back there?

Then write, then verify:

```bash
before=36616
after=$(wc -c < ~/haksterAi/.hakster/MEMORY.md)
[ "$after" -gt "$before" ] && echo "OK grew: $before -> $after" || echo "STOP: file shrank"
```

## 4. How to write a good knowledge entry

Append a section shaped like this, so future-you can tell verified fact from old guess:

```markdown
## 2026-11-07 — <short title of what changed>

- Verified: <the fact, checked against the running system, with the command or file:line>
- Changed: <what was added/patched, file paths>
- Why: <the owner request or the failure it fixes>
- Not verified: <anything you could not confirm — say so plainly>
```

Rules for the content:

- Only **verified behaviour**, real file paths, real commands, real decisions.
- Never tokens, passwords, API keys, `.env` values, session cookies, or customer data. Say
  "secret stored in the existing `.env`" instead of the value.
- Never present planned or untested behaviour as working. Write "not yet verified" instead.
- Never inflate: if a service returned 200 on one page, that is what you write, not "the site
  works".

## 5. When something looks broken

Order matters. Diagnosing is free; changing is not.

1. **Read only.** Look at service state and logs (`pm2 list`, `pm2 logs <name> --nostream
   --lines 30`, `systemctl status`, `curl -sI http://127.0.0.1:PORT/`).
2. **Write down what you saw** — the exact command and its output, not your conclusion.
3. **Find the last good state.** `ls -lt <file>.bak-*` shows the newest backups; a brain file
   with an unexpected low size means a previous write went wrong.
4. **Fix the application, not the configuration.** Code, UI, docs, fallbacks — that is where
   fixes belong.
5. **If your own brain looks damaged, restore the newest good `.bak-*` over it** — that is the
   one and only case where replacing a brain file is correct, because restoring a verified
   backup returns you to a known-good prior state. Do not *then* re-apply the broken edit.
6. **Never** respond to a failure by disabling, replacing, or restarting a healthy service.

### Recovery from a bad brain edit

```bash
# 1. find the backups, newest first
ls -lt ~/haksterAi/.hakster/MEMORY.md.bak-*
# 2. compare sizes - the good one is the one that was large before the bad write
wc -c ~/haksterAi/.hakster/MEMORY.md.bak-*
# 3. copy the good one back (keeping the damaged one as evidence, never delete it)
cp -p ~/haksterAi/.hakster/MEMORY.md ~/haksterAi/.hakster/MEMORY.md.damaged-$(date -u +%Y%m%dT%H%M%SZ)
cp -p ~/haksterAi/.hakster/MEMORY.md.bak-<good-stamp> ~/haksterAi/.hakster/MEMORY.md
# 4. verify
wc -c -l ~/haksterAi/.hakster/MEMORY.md
```

The damaged copy stays on disk. No deletions, ever.

## 7. Failure signs and what they mean

| Symptom | Likely cause | Correct response |
| --- | --- | --- |
| Brain file suddenly much smaller | a write replaced instead of appended | restore newest good `.bak-*`; keep the damaged copy |
| Section headings count dropped | consolidation pass or manual rewrite | restore from backup, report it |
| Session no longer remembers prior work | `MEMORY.md` / `memory_summary.md` lost content | check sizes against the floor table |
| Agent refuses tools / odd routing | prompt or rules file was edited | restore `.bak-*`, never "fix" by changing models |
| Service down after your change | you restarted or reconfigured something you did not need to | report it; do not restart again to "settle" it |
| Duplicate process or extra memory use | nothing is broken | report the reading; never kill it |

## 8. What you are allowed to do without asking

- Read anything, including config, for diagnosis.
- Create **new** files, including new docs, skills, and scripts.
- Append dated sections to your own knowledge, memory, and rules files after a backup.
- Patch application code, with a backup of each file first and a syntax check after.
- Run read-only checks: `curl`, `ss`, `pm2 list`, `systemctl status`, `wc`, `grep`, `git status`.

## What always requires an explicit, specific yes

- Editing any config file listed in Law 3.
- Stopping, starting, restarting, or reprioritizing any service or process.
- Touching a Cloudflare tunnel, its config, its credentials, or its DNS.
- Rewriting, consolidating, or deleting anything in your brain.
- Deleting any file at all, in any project.
