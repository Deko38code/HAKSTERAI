## 3. Missing and conflicting prices

1. **Two config files, one of them a decoy — the real finding.** The server loads
   `server/.env` (`index.js:7`, `path.join(__dirname,'../.env')`, `override: true`), which holds the
   correct `29999 / 9999 / 99999`. The repo-root `.env` holds **`29000 / 10000 / 120000`** and is read
   by nothing at runtime. Anyone "fixing" prices in the root file would see no effect — and anything
   that *does* read the root file (the release worker symlinks `.env` from the repo root) would get
   the wrong numbers. Recommend consolidating to one file; **do not edit either without approval**.
2. **`STRIPE_PRICE_FREE` is empty** in both files. Harmless today (the free row renders "Free" with
   no checkout button, `plans.astro:158`), but the variable's presence implies a price that does not
   exist. Either populate it with a real $0 price or remove the variable — a decision, not a patch.
3. **Five inactive legacy HaksterAI prices** remain on the account ($4, $19, $99, $190, $990 —
   `price_1TyL5x…` … `price_1TyL61…`). They cannot be used for new checkouts (inactive) and are
   historical records. **Do not archive or delete them** — they may back existing subscriptions'
   history.
4. **Three junk-named live products** ("29$/monthly", "29$/mo recurring price",
   "290$/year-…") duplicate each other's intent. They are active and could be picked up by a
   name-based lookup. Flagged for owner review; not touched.
5. No product in the catalog is missing a price.

## 4. Proposed pricing component

The catalog already exists in the right shape — one server-side source of truth (`PRICING_CATALOG`,
`index.js:380-520`) merged with live Stripe prices by `refreshPricesFromStripe()`. Keep it, and make
the two rules explicit rather than implicit:

- **Display amount = Stripe `unit_amount`**, not a local constant. Today the static entry wins
  (`index.js:902` skips a live entry whose id is already mapped), so display and charge agree only
  because the constants happen to be right. Make the live price authoritative and the constant a
  fallback used only when Stripe is unreachable — then a price change in Stripe can never disagree
  with the page.
- **Checkout takes a plan id, never an amount.** Already true: the browser posts a `priceId`
  (`plans.astro:60`), the server resolves it through the catalog to a Stripe price id
  (`index.js:8180-8195`). Keep it.

Proposed shape:

```
planCatalog(planId) -> { planId, productName, priceId, amount, currency, interval,
                         introAmount?, introCoupon?, entitlements[], source: 'stripe' | 'fallback' }
```

with a boot-time assertion: every mapped `priceId` exists, is `active`, and its `unit_amount` equals
the configured amount — logged loudly on mismatch, never silently corrected.

## 7. Webhook security — code path verified, no live exercise

| Requirement | Status | Evidence |
|---|---|---|
| Raw body for signature | done correctly | `express.json()` explicitly skips `/api/stripe/webhook` (`index.js:759`); the route mounts its own `express.raw({type:'application/json'})` at `index.js:1197` |

| Missing secret fails closed | yes | 503 when `STRIPE_WEBHOOK_SECRET` is absent (`1200`) |
| Payment status checked, not assumed | yes | `checkout.session.completed` requires `payment_status ∈ {paid, no_payment_required}` (`1218`) |
| Entitlements not granted by redirect | yes | `/api/stripe/claim` (`1618`) only returns the account the **paid webhook** already created; the claim row must exist, and the update is single-use and atomic (`1629-1630`) |
| Idempotent handling | **partial** | delivery outcomes are upserted into `stripe_webhook_events` (`ON CONFLICT(id)`, `990`), and the state writes are upserts, so a replay does not double-apply. There is **no explicit "this event id was already applied" gate** before the switch. Recommend adding one — cheap, and it turns "probably safe" into "provably safe". |

**Not claimed:** none of this was exercised against a live delivery. It is a code-path verification.

## 8. PhantomIDE reporting design (read-only, least privilege)

PhantomIDE receives a **projection**, never credentials and never the Stripe account:

```
{ at, project:"haksterai", kind:"pricing",
  catalogHash, planCount,
  plans:[{planId, priceId, amount, currency, interval, active, source}],
  drift:  [{planId, configured, stripe, field}],   // mismatches, if any
  checks: [{name, ok, detail}] }                    // e.g. "price exists", "amount matches"
```

Outbound only, with retry + dedup (same contract as the release reporter): idempotency key
`project:kind:catalogHash`, exponential backoff, dedup by key, and a local spool so a Parrot outage
never blocks anything. **No Stripe key is ever sent**, and PhantomIDE gets no ability to call Stripe.

## 9. Release-engine Stripe validation stage

Proposed: a `stripe-verify` stage **before** the switch, that never writes to Stripe:

- every mapped price id exists, `active: true`, and `unit_amount`/`currency`/`interval` match config;
- the product named in the plan resolves to exactly one active product (guards the duplicate-name
  risk in §3.4);
- the webhook endpoint exists and its enabled events include the five handled types;
- result is recorded in the release journal and **a failure blocks the candidate without touching the
  serving site** — the running release keeps serving.

A build must never create or modify a Stripe resource; this stage only reads.
